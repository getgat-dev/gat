# Releases

The [release workflow](../.github/workflows/release.yml) publishes GitHub Release
archives. `task release` builds a local binary only. There is no crates.io
publishing step. Run the commands below from the repository root.

## Prepare

1. Update the root package version in `Cargo.toml`, refresh `Cargo.lock` with
   `cargo check`, and commit both. The release tag must be `v<package-version>`.
2. Run `task check` and `task docs:validate`. Run `task docs:generate` first if
   CLI or configuration documentation changed. Merge through a PR and wait for
   CI on the intended `main` commit.
3. Review the draft notes generated by
   [Release Drafter](../.github/release-drafter.yml) on pushes to `main`.
   Align the draft's tag and title with the package version; the version
   suggested from PR labels does not update Cargo. Leave the draft unpublished.
4. Run **Release** manually on `main` and confirm the run tested the intended
   release commit. Manual runs validate without publishing. PRs exercise the
   release matrix only when they change a path listed in the workflow;
   version-only PRs need a manual run.

Builds use `--locked` and the pinned `RELEASE_RUST_VERSION`. Preparation checks
that this Rust version matches the root MSRV and that the GNU glibc baseline
matches the installer. Update these pins together when changing compatibility.

## Build matrix and validation

| Platform | Targets | Build and execution |
| --- | --- | --- |
| Linux GNU | `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` | cargo-zigbuild targeting glibc 2.28; native runners and Rocky Linux 8 tests |
| Linux musl | `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl` | Static cargo-zigbuild; native runners and Alpine tests |
| macOS | `x86_64-apple-darwin`, `aarch64-apple-darwin` | Cargo on ARM64 macOS; Intel binary tested through Rosetta 2 |
| Windows | `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc` | Cargo and tests on native x86_64 and ARM64 runners |

Archives are `gat-v<VERSION>-<TARGET>.tar.gz` on Unix and
`gat-v<VERSION>-<TARGET>.zip` on Windows. Each contains a matching directory
with `gat` or `gat.exe`, `README.md`, and `LICENSE`. Public releases contain
all eight archives and `SHA256SUMS`; individual `.sha256` files remain CI artifacts.

Each build extracts its archive and runs the shared `release_artifact_` tests
against that executable: exact version, help, initialization and hooks,
file-remote push/pull, and configuration isolation. Linux also passes the ABI
and runtime checks below. After all builds pass, the workflow verifies the
asset inventory and checksums, then creates and verifies provenance attestations
against the source commit and signing workflow. Fork PRs skip attestation;
tag releases require it before publishing.

## Publish

Tag the validated commit and push that specific tag. For package version
`0.1.0`, from the intended commit:

```sh
git tag v0.1.0
git push origin v0.1.0
```

The tag push runs the full pipeline again. Only this trigger can publish.
After validation and attestation, the final job uploads the archives and
`SHA256SUMS` and publishes the matching draft, creating a release if needed.
Do not publish the draft manually: the workflow refuses to modify public releases.

Confirm all assets are present, then smoke-test the pinned release through
both installers on supported platforms. See the
[installation guide](../docs/installation.mdx) for commands and checksum
verification. Local installer fixtures do not test published downloads.

## Retry or fix a release

For transient runner, network, or upload failures, rerun the failed tag workflow
while the release remains unpublished. CI artifacts expire after seven days;
rerun all jobs if they need rebuilding. A manual workflow run cannot publish.

For source or workflow fixes, merge a PR and release a new version/tag. Keep
existing tags fixed. Correct public releases with a new version; the publishing
guard prevents asset replacement.

## Run acceptance tests locally

Extract an archive and point `GAT_TEST_BIN` at its executable. On Unix:

```sh
GAT_TEST_BIN=/absolute/path/to/gat cargo test --locked --test cli_integration release_artifact_
```

On Windows, in PowerShell:

```powershell
$env:GAT_TEST_BIN = 'C:\absolute\path\to\gat.exe'
try {
    cargo test --locked --test cli_integration release_artifact_
} finally {
    Remove-Item Env:GAT_TEST_BIN
}
```

### Linux compatibility

[The ABI checker](../tools/check-linux-release.sh) checks ELF class, byte order,
architecture, and GNU glibc symbol requirements. Musl binaries must have neither
an ELF interpreter nor shared-library dependencies. Its fixtures run with
`task test:install`.

[The runtime helper](../tools/test-linux-release.sh) checks the ABI, then runs
acceptance tests in Rocky Linux 8 (GNU) or Alpine (musl). The Rust harness runs
on the host; Gat processes run in the container. Only the candidate and fixture
directory is mounted. On Linux, with Docker, `readelf`, and Rust installed:

```sh
bash tools/test-linux-release.sh /absolute/path/to/gat x86_64-unknown-linux-gnu 2.28
```

Use the matching target triple for other Linux variants. For ABI inspection
alone, invoke `tools/check-linux-release.sh` with the same arguments.

When changing the GNU baseline, update `GLIBC_VERSION` in the workflow,
`MIN_GLIBC` in `docs/install.sh`, the GNU image in
`tools/release-runtime.Dockerfile`, and the installation guide. Runtime tests
check that the container's glibc version matches the declared baseline.
